# Quick Definition Table

| Key | Definition |
|------|------------|
| **Primary Key** | Official unique identifier of a table |
| **Foreign Key** | References the Primary (or UNIQUE) Key of another table |
| **Candidate Key** | Minimal key that can uniquely identify a row |
| **Alternate Key** | Candidate Key not selected as the Primary Key |
| **Composite Key** | Two or more columns together uniquely identify a row |
| **Super Key** | Any column(s) that uniquely identify a row, including unnecessary columns |
| **Surrogate Key** | Artificial key generated by the system |
| **Natural Key** | Real-world business identifier |

# Which Key Should You Choose?

## Scenario 1

### Customer Table

```text
CustomerID
Email
Phone
```

Recommended

```
CustomerID

↓

Primary Key (Surrogate)

Email

↓

UNIQUE
```

## Scenario 2

### Books

```text
ISBN

Title

Author
```

Recommended

```
ISBN

↓

Natural Key
```

---

## Scenario 3

### Student Enrollments

```text
StudentID

CourseID
```

Recommended

```
Composite Key

or

EnrollmentID

+

UNIQUE(StudentID, CourseID)
```

Enterprise systems usually choose the second approach.

## Scenario 4

### Orders

```text
OrderID

CustomerID
```

Recommended

```
OrderID

↓

```

Here:

- `CustomerID` → Surrogate Primary Key
- `Email` → Alternate/Natural Business Identifier
- `CustomerID` in `Orders` → Foreign Key

# Enterprise Architecture Pattern

Modern applications usually follow this design:

```text
Primary Key

↓

Surrogate Key

↓

Business Data

↓

UNIQUE Constraints
```

Example

| Column | Constraint |
|----------|------------|
| CustomerID | PRIMARY KEY |
| Email | UNIQUE |
| PassportNo | UNIQUE |
| MobileNo | UNIQUE (Optional) |

This keeps relationships stable while enforcing business rules.

## Which key is the official identifier?

✅ Primary Key

## Which key connects two tables?

## Which key is generated by the database?

✅ Surrogate Key

---

## Which key comes from business data?

✅ Natural Key

## Which key contains unnecessary columns?

✅ Super Key

---

✅ Primary Key

## Which Candidate Keys are not selected?

✅ Alternate Keys

# Common Mistakes

❌ Thinking every unique column is a Primary Key.

---

❌ Using Email as a Primary Key.

---

❌ Assuming Composite Keys are always bad.

They are appropriate in many junction tables.

---

❌ Believing Natural Keys should never be used.

Some Natural Keys (ISBN, VIN, Passport Number) are excellent choices.

---

❌ Forgetting to add `UNIQUE` constraints when using Surrogate Keys.

---

# 💡 Did You Know?

Most enterprise applications actually use **multiple key types together**.

Example:

| Column | Key Type |
|----------|----------|
| CustomerID | Surrogate + Primary Key |
| Email | Alternate + Natural Key |
| PassportNo | Alternate + Natural Key |
| CustomerID (Orders) | Foreign Key |

A single table can contain **four or more different key types** working together.

# Best Practices

✅ Use a Surrogate Key for Primary Keys in enterprise systems.

✅ Keep business identifiers as `UNIQUE`.

✅ Use Composite Keys only when appropriate.

✅ Choose the smallest Candidate Key.

✅ Avoid updating Primary Keys.

✅ Document every relationship.
